# Single DGX Spark recipe backlog

Research snapshot, 2026-11-20. This backlog targets one 128 GB GB10, arm64/SM121. Benchmarks below come from the recipe authors or upstream maintainers and still need to be reproduced on the target. The catalog's one-Spark filter lists 11 recipes, with some models represented by multiple engines. The GitHub organization has additional single-device recipes. [NVIDIA hardware specifications](https://www.nvidia.com/en-us/products/workstations/dgx-spark/) · [Filtered catalog](https://mia-ai.net/models?for=spark%3A1) · [Full catalog](https://mia-ai.net/models) · [MiaAI-Lab repositories](https://github.com/MiaAI-Lab/)

## Qwen3.8 Flash Next

1. **Capture the running profile first.** Record the actual checkpoint revision or shard hashes, engine image ID/digest, patches, launch flags and observed memory. Preserve the same checkpoint and context during reproduction. Treat the serving paths below as separate experiments. In particular, NVIDIA publishes distinct `NVFP4` and `FP4-Local` exports, with different retained precision, layouts and runtime requirements. [NVIDIA NVFP4 model card](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4) · [NVIDIA FP4-Local model card](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local)
2. **Mia vLLM TP1.** The stock path uses `Mia-AiLab/Qwen3.8-Flash-Next-NVFP4` (~99 GiB) and a ~27 GiB memory-mapped PLE table. Its sample profile configures 262,144 tokens, MTP3, FP8 KV, BF16 recurrent state and four sequence slots. The older sparkDash sweep measured 48.7 C1 prose and 162.9 aggregate C8 under its stated conditions. Sybil's registry recorded HTTP 401 for the historical model pin `925d7be6c14c` and removed that entry, so verify availability or the existing cache before attempting a fresh setup. An optional path serves `nvidia/Qwen3.8-Flash-Next-NVFP4` on vLLM 0.30.0 with a ~124 GiB checkpoint and ~48 GiB packed PLE table. Mia reported 784 successful requests in a one-hour mixed-traffic soak on that lane. [Mia recipe and measurements](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark) · [Historical recipe commit d038090](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/commit/d03809008834124e80223c3482f2ddb59577a48f) · [Registry pin removal](https://github.com/sybil-solutions/local-ai-registry/issues/214)
3. **NVIDIA QAD FP4-Local.** NVIDIA documents a GB10 vLLM TP1 path with a format-compatible B12X container, on-disk PLE, FP8 KV and a 262,144-token configuration. Its reported 1M KV tokens describe pool capacity. Mia's independent TensorFold Zig path pins the same QAD checkpoint, uses FP8 KV and configures up to five 262,144-token requests. The README documents engine v1.2.7 (`93a2e93e`) and a retrieved 199,730-token needle, tool/vision checks and context-boundary checks on the patched build. The catalog's 55.6 tok/s C1 prose and 156.1 tok/s C5 aggregate belong to the older v1.1.4 run. The QAD-focused v1.2.7 recipe excludes INT4 support and refers back to `db281878` for INT4-AutoRound. That historical INT4 path uses five routed experts per token versus ten on QAD, has a separate quality trade-off and needs its own acceptance run. [NVIDIA GB10 launch](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local#nvidia-dgx-spark) · [TensorFold recipe](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark-TensorFold) · [Pinned QAD revision](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/tree/b9ce18a6887e18c089fdea8509a33e63429a3300) · [Historical catalog benchmark](https://mia-ai.net/models/Qwen3.8-Flash-Next-Single-DGX-Spark-TensorFold)
4. **Blazux vLLM 0.33.** A separate GB10 implementation stages an NVIDIA hybrid checkpoint and reads PLE from NVMe. Upstream measured on one ASUS GX10, reporting retrieval at 499k with `mtp-fast` and at 990k with optional 1M profiles. Budget roughly 140 GB for weights plus 13 GB for the prepared layout. Its separate GB10 comparison found the matched MTP2 profile more suitable on that host than the faster profile for its tested mix, so qualify long-context profiles independently. [Recipe and measured workloads](https://github.com/blazux/qwen3.8-Flash-DGX) · [Historical commit bd60fcb](https://github.com/blazux/qwen3.8-Flash-DGX/commit/bd60fcb1b492ca920f74df7462f05da7b6d98f73)

## Other published one-Spark recipes

**Next on this Spark, package Qwen3.8 27B on TensorFold.** It has a prior local deployment and makes a useful matched comparator. For a second engine, Qwen3.6 35B-A3B and Nemotron 3.5 Lightning have native arm64 paths and lighter checkpoints. DeepSeek and GLM are later candidates where long-context fit and quantization quality need separate qualification.

- **Qwen3.6 35B-A3B.** Unsloth mixed FP8/NVFP4, vLLM GB10 B12X + MTP, 262,144 configured. The authors measured 95.1 C1 and ~317 aggregate C8 on GB10. Freeze the image digest before using the source's moving tag. [Source recipe](https://github.com/MiaAI-Lab/Unsloth-Qwen3.6-35b-NVFP4-DGX-Spark)
- **Nemotron 3.5 Lightning 30B-A3B.** SGLang NVFP4 + DSpark, ~21 GiB across target and draft. The Spark setup reports a ~4.93M shared token pool from ~14 GiB target KV plus ~28 GiB separate draft KV, with a native 1M per-request limit. The 48 request slots can serve short sessions and share the same pool. [Mia Spark recipe](https://github.com/MiaAI-Lab/Nemotron3.5-Lightning-DGX-Spark-RTX-5090-6000-PRO) · [NVIDIA engine cookbooks](https://github.com/NVIDIA-NeMo/Nemotron/tree/main/usage-cookbook/Nemotron-3.5-Lightning)
- **Qwen3.8 27B.** The TensorFold recipe uses MLX-format 4-bit weights on CUDA with DFlash2, ~15 GB checkpoint and up to 78 GiB reserved KV. Mia measured ~97 GiB reserved by the server with the full pool. SGLang instead defaults to ~24 GB NVFP4 with a BF16 head; its tested MTP route can extend from 262,144 to 1M via YaRN, while DSpark and DFlash2 on the pinned builds are capped at the native window. [TensorFold](https://github.com/MiaAI-Lab/Qwen3.8-27B-DGX-Spark-TensorFold) · [SGLang](https://github.com/MiaAI-Lab/Qwen3.8-27B-SGLang-DGX-Spark)
- **Nemotron 3.5 Bolt 74B-A9B.** TensorFold Zig with IQ2_XXS experts, NVFP4 Mamba and Q8_0 attention. The 24 GB pack used 51.1 GB unified memory with the test defaults. Latest source results use their own shared or distinct prompt benchmark, so keep the settings with the score. [Source recipe](https://github.com/MiaAI-Lab/Nemotron-3.5-Bolt-TensorFold-DGX-Spark)
- **Muse Glimmer 30B.** vLLM with Red Hat NVFP4 (~19 GB), vision and DFlash. GB10 measured ~35 tok/s with DFlash. Its configured 262,144 window extrapolates from native 131,072, so include a retrieval test before advertising the extended window. [Source recipe and hardware-specific results](https://github.com/MiaAI-Lab/Muse-Glimmer-30B-DGX-Spark-RTX-5090-6000-PRO)
- **Laguna S 2.1.** vLLM 0.25.1, poolside NVFP4 (~71 GB) plus ~2 GB DFlash, TP1, 262,144 configured. Check Hugging Face access and isolate the Spark settings from the RTX PRO 6000 variant in the same repository. [Source recipe](https://github.com/MiaAI-Lab/Laguna-S-2.1-DGX-Spark-RTX-6000-PRO)
- **Ling 3.0 Flash.** SGLang INT4 + DSpark measured 83 C1 and 136 aggregate C6 on one GB10. Higher-throughput `MEM_FRACTION_STATIC=0.87` left ~9.5 GiB available at idle. Use a lower memory fraction to qualify first and repeat under long-prefill load. [Source recipe](https://github.com/MiaAI-Lab/Ling-3.0-Flash-SGLang-DSpark-DGX-Spark)
- **Ornith 1.5 122B.** TensorFold EXL3-EAQ ~4 bpw + DFlash2, ~62 GiB checkpoint and ~92 GiB host availability at launch by default. Although 262,144 is configured, the published recipe reports retrieval at 32k and prefill to 131k. [Source recipe](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold) · [Pinned model revision](https://huggingface.co/Mia-AiLab/Ornith-1.5-122B-EXL3-EAQv1-4-bpw/tree/9c5c913b3de1eef901520d6fedaf450044ea0423)
- **DeepSeek V4 Flash 0731.** Mia's standalone EXL3 launcher uses a custom vLLM B12X backend, compressed KV and DSpark K5. Published deep-context config is 384k C1 with exact needle recall at 370,104 tokens. It uses ~107 GB local weights and a high memory utilization setting of 0.94. [Single-Spark source and stress tests](https://github.com/MiaAI-Lab/DeepSeek-v4-Flash-One-DGX-Spark)
- **GLM-5.3-Flash.** Higher-pressure option. One-Spark vLLM EXL3 2.05 bpw + DFlash2 has published structured/prose results of ~64/~25 tok/s (K7) and explicitly distinguishes 182 active-stream aggregate from ~91 full-batch wall throughput. A separate 0xSero prototype uses native MTP with a K2 checkpoint (~102 GiB engine load) and reported ~19 sampled tok/s through 260k. Record its exact checkpoint and measured artifact size because its project description and README give different nominal bpw figures. Check fidelity at the chosen quant level and keep these distinct from Mia's 2–4 Spark recipes. [DFlash2 recipe](https://github.com/gitcommit90/glm-5.3-one-spark) · [Native MTP recipe](https://github.com/0xSero/GLM-5.3-Flash-EXL3-1x-DGX-Spark) · [Mia multi-Spark recipe](https://mia-ai.net/models/GLM-5.3-Flash-DGX-Sparks-1104)
- **DeepSeek V4.1 Flash 1017.** Experimental qualification despite published one-device runs. The ds4-dfm-rs VQ ~1.6-bit path publishes one-sequence results with only ~5 GB free during its benchmark and depends on NVMe and working `io_uring`. A TensorFold hybrid offload variant gets four configured 256K slots with SAGE EXL3 1.62 bpw routed experts, throttles expert participation by default and reports 10–19 tok/s after cache-displacing prefill. Require workload fidelity, sustained latency and memory evidence before promoting either profile. [ds4-dfm-rs recipe](https://github.com/dedene/DeepSeek-V4.1-Flash-1017-DGX-Spark) · [TensorFold hybrid offload](https://github.com/Loke-60000/deepseek-v4.1-1017-1xGB10-recipe)

## Sybil sources for other hardware

- **`qwen38-flash-next-3090-usb-offload`.** Corrected repository slug. The Mac mini M4 stack uses Strata and USB CUDA shim/kernels, a 24 GB RTX 3090 dock and a split EXL3 3.05 bpw / IQ3_S setup. Config F's 200k setup and performance are specific to that host and offload design. [Source](https://github.com/sybil-solutions/qwen38-flash-next-3090-usb-offload) · [Config F release](https://github.com/sybil-solutions/qwen38-flash-next-3090-usb-offload/releases/tag/config-f-2026-10-17)
- **`qwen38-b70` and `qwen38-flash-next-b70-offload`.** The former is Qwen3.8 **27B** in llama.cpp SYCL/Q4_K_M. The latter is **Flash Next** in SGLang XPU/EXL3 with host and staged NVMe tiers. Its 25.6 tok/s 32 GiB-cap result used an Arc Pro B70, EPYC host and four NVMe drives in RAID0. The authors report a failing fresh-server chat gate for their registry candidate. Both archived repos have active source paths in `qwen-serve`. [Active source map](https://github.com/sybil-solutions/qwen-serve#readme) · [Archived 27B](https://github.com/sybil-solutions/qwen38-b70) · [Archived Flash Next and measurements](https://github.com/sybil-solutions/qwen38-flash-next-b70-offload)
- **`glm-flash-lite`.** GLM EXL3 3.05 bpw (~125 GB checkpoint) on a 24 GB RTX 3090 with AVX2 CPU expert tier and RAM/NVMe. Its benchmark host was an x86 EPYC server, so carry over evidence collection practices and qualify a GB10-specific runtime separately. [Source](https://github.com/sybil-solutions/glm-flash-lite)

## Qualify each profile

1. Resolve the launcher to a full Git SHA, the image to its arm64 digest, and weights and draft to their upstream revisions. Record required artifact access, prepared-file checksums, cold and warm disk usage, engine patches, driver, CUDA and model license. The historical commit links above identify source evidence. Resolve every moving source to a new verified pin before deployment.
2. Start with one instance and short context. Track host `MemAvailable`, swap deltas, KV capacity, restarts, time to ready and warm/cold TTFT through load. Increase length and parallel requests separately. Record configured per-request length, longest successful retrieval and shared KV tokens as separate fields.
3. Run chat, reasoning, tools, structured outputs and streaming through the intended client, plus image/video if advertised. Compare deterministic and sampled runs where supported, record workload and speculation settings, then measure C1 and C4/C8 wall throughput and run a mixed-traffic soak. Preserve raw outputs and failure cases alongside the exact configuration.
