## How the model works

Suppose you send “I left the key on the kitchen” and ask the model to continue. A **tokenizer** splits the text into pieces and assigns each piece an integer ID. A piece can be a word, part of a word, punctuation, or whitespace. The ID is an address. Looking it up in a table gives the model an **embedding**, a list of 2,560 learned numbers. The table and the other learned numbers in the checkpoint are its **weights**. They stay fixed throughout the conversation. The numbers computed *from* your prompt, including the representation of “kitchen” and the record of what preceded it, are request-specific **state**. Two requests can share the weights and produce very different states. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

To generate the next piece, the model transforms each input embedding through 48 layers. By the last layer, the vector at the final position depends on the entire sequence of computations leading there. A separate learned matrix called the **language-model head** converts that vector to 248,320 scores, one for each row of the padded vocabulary. Turning eligible scores into probabilities is called *softmax*. For illustration, “ counter” might have probability 0.55 and “ table” 0.30, with 0.15 spread across other possibilities. A greedy decoder picks the highest score. A sampling decoder draws from the distribution after applying the request’s sampling settings. If it emits “ counter”, that ID becomes an input for the next step. These example probabilities illustrate the decision and are independent of the benchmark. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

### Follow the final prompt token

```text
token IDs -> 2,560 numbers per token -> four residual branches
            layer 2 also reads short token sequences from a learned table
            12 groups of four layers, each with its own weights
                3 × (Gated DeltaNet -> mixture of experts)
                1 × (Qwen Sparse Attention -> mixture of experts)
            final representation -> vocabulary scores -> next token ID
```

**How a phrase gets a representation of its own.** The input embedding for “kitchen” starts the same wherever that token ID appears. At layer 2, a per-layer embedding (PLE) lookup also uses adjacent **n-grams**, sequences of token IDs ending at this position. Assuming one token per word for this example, “the kitchen” provides a bigram and “on the kitchen” a trigram. Their IDs determine table addresses before deeper layers run. The model reads the selected vectors and incorporates the local phrase information into that position. The nominal n-gram vocabulary is 20 million and the tables add about 51 billion parameters. Each position needs only its selected rows. Reading those rows in advance can overlap the lookup with other work. [Qwen on n-gram embeddings](https://arxiv.org/html/2608.30320v1#S2.SS3) · [Checkpoint settings](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

**What carries a feature from layer to layer?** A residual connection lets a layer add an update to information already present. Flash Next maintains four 2,560-number branches per token. Before each token mixer or expert sublayer, Gated Residual normalizes each branch and calculates read weights from their contents through a 320-wide intermediate projection. The read weights can differ for each branch and each coordinate. The sublayer receives one combined vector and computes one update. A separate learned gate sets how much of that update to add back to each branch, using one scalar per branch. A feature can therefore remain strong on one branch while later layers choose a different mixture to read. These four branches belong to one token in one request. [Qwen’s Gated Residual design](https://arxiv.org/html/2608.30320v1#S2.SS2) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

**How the first three layers in a group remember preceding text.** A Gated DeltaNet (GDN) layer maintains a matrix of associations for each recurrent value head. From the current vector it computes a query, a key and a value. In plain terms these are a question to ask of memory, an address for an update and information to store. A short learned filter blends features from up to four consecutive positions. The layer decays some previous state, looks up what the key already predicts, and writes a gated correction toward the new value. Its query reads the updated state to produce this token’s output. For example, “counter” later in a sentence can change an earlier association between a key and a location. Real addresses are learned vectors, so multiple associations can interact. The 36 GDN layers use 16 query/key heads and 48 value heads, each 128 numbers wide. Their main recurrent matrices stay the same size as a conversation grows. [Qwen on the gated delta update](https://arxiv.org/html/2608.30320v1#S2.SS1.SSS1) · [Checkpoint dimensions](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

**How the fourth layer can retrieve an old detail.** Qwen Sparse Attention (QSA) keeps token-level keys and values from earlier positions. Suppose the prompt contains thousands of lines and one identifies the key’s owner. The current position first scores summaries of complete four-token blocks. The indexer averages keys within each block and uses four 128-wide query heads with one shared key head. It ranks the blocks, selects up to 512 and expands them back into individual positions. The main attention reads the selected tokens’ original keys and values, so a token can contribute differently from its neighbors. The published rule also includes the current incomplete block. The 2,048-token budget describes the selected complete-block content. The indexer can find a remote block even if many tokens have arrived since. It can also overlook one. [Qwen’s QSA selection rule](https://arxiv.org/html/2608.30320v1#S2.SS1.SSS2)

Each of the 12 QSA layers has 24 main query heads sharing two key/value heads. A *head* is one set of projections that can learn a different way of matching features. The main heads are 256 numbers wide. Rotary position embeddings rotate 64 coordinates according to position, giving the matching calculation information about where tokens appeared. Selected positions receive normalized attention weights, and their weighted values form the layer’s retrieval result. The indexer reduces how much detailed attention to compute at a given step. Older keys and values must remain accessible because a different question can select different blocks. [Qwen architecture report](https://arxiv.org/html/2608.30320v1#S2.SS1.SSS2) · [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview)

**What happens after every memory read.** A mixture of experts (MoE) transforms each position’s updated features. There are 512 routed expert networks per layer. A small router scores them for this input and selects ten. Each selected expert projects through an intermediate width of 640, applies a learned gated transformation and returns an update in the language model’s width. Their weighted outputs join the contribution of a shared expert that runs for every token. The next position can select a different ten. Qwen counts 125 billion parameters in the main model with about six billion active per token, then reports the 51 billion n-gram parameters and four billion multi-token prediction parameters separately. Sparse routing saves arithmetic while the engine still needs access to the pool of possible experts. The final read from the branches reaches the output head described above. [Qwen model overview](https://huggingface.co/Qwen/Qwen3.8-Flash-Next#model-overview) · [Pinned configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json)

**Where images and drafts enter.** Images take a different route into the same language layers. A 27-layer vision encoder with width 1,152 and 16 attention heads reads 16-by-16-pixel patches. Its configuration groups two time slices per temporal patch and merges 2-by-2 groups spatially. A projection produces 2,560-wide visual features that fill visual positions in the prompt. The output is still a sequence of text tokens. At the other end, a separately trained, single-layer **multi-token prediction** (MTP) module uses model features and token embeddings to propose subsequent IDs. Its proposals can accelerate generation when checked together by the main model. Qwen’s architecture illustration describes reuse of QSA index selections across draft iterations. The engine determines how that part executes on the Spark. [Vision and MTP configuration](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/config.json) · [Qwen architecture, figure 1](https://arxiv.org/html/2608.30320v1#S1)

## How this recipe runs it on one DGX Spark

### What gets built and where the model lives

One GB10 uses one shared pool of physical memory for the CPU and GPU. Placement still matters. The GPU runs the language model’s matrix multiplications, while the CPU can retrieve the few embedding rows needed for a phrase. The engine and operating system share space with weights, active requests, temporary computation and file-backed pages. Disk space for installing the weights is a separate budget. The hardware is sold as 128 GB. Linux reported 121.69 GiB on the tested machine. [Observed hardware and runtime](../results/running-profile.json) · [NVIDIA DGX Spark specifications](https://www.nvidia.com/en-us/products/workstations/dgx-spark/)

The wrapper’s `fetch` command stages the Mia recipe at commit `b956dba8a468f1cf376d60bbbd9b9ed51ff2f0a9`. Its `prepare` command builds TensorFold 1.2.7 from `93a2e93ecebff8aa52b88e58c5dd222516e69c5f` with the recipe patches and pinned NVIDIA base image, stages the NVIDIA FP4-Local checkpoint at `b9ce18a6887e18c089fdea8509a33e63429a3300`, and records the resulting Docker image ID. The data directory holds source in `upstream-<commit>/`, build records in `state/`, kernels in `kernels/` and weights under `huggingface/hub/` by default. Docker stores the image layers separately. A fresh install calls for about 160 GiB free disk and an estimated 107 GiB available memory at startup. The November 22 clean build answered a chat request. The timings below are from the November 20 resident deployment. [Wrapper](../bin/recipe.py) · [Installation](reproduce.md) · [Validation history](../results/README.md)

**Quantization** represents numerical values with fewer bits, usually sharing a scale among a small group so that small and large values remain useful. This *FP4-Local* export uses four-bit floating-point values for the decoder’s routed experts, groups of 16 with compressed scale factors, and microscaled eight-bit values on selected attention and shared-expert projections. NVIDIA used quantization-aware distillation, training the reduced-precision model against a higher-precision teacher. The MTP experts and vision tower also have their own formats. The pinned build reads the roughly 26.8 GiB NVFP4 n-gram table from disk on the host through Linux’s page cache. Repeatedly accessed pages can therefore occupy RAM, and row reads can have different costs depending on cache warmth. [NVIDIA checkpoint](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-FP4-Local/blob/b9ce18a6887e18c089fdea8509a33e63429a3300/README.md) · [Pinned TensorFold placement](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark-TensorFold/blob/b956dba8a468f1cf376d60bbbd9b9ed51ff2f0a9/README.md)

### From a chat request to the first streamed token

After verifying the prepared image, `start` mounts the checkpoint cache read-only and binds `127.0.0.1:18889`. Send the model ID `Qwen3.8-Flash-Next` to `/v1/chat/completions`. The chat template turns the ordered roles, messages and thinking setting into model input. For media, an `image_url` or inline MP4 `video_url` part invokes the local visual path. Sampled video frames consume visual token positions and encoder workspace before the answer can start. The measured configuration enables vision and video with a 16,384-token media budget. In the local fixtures the model identified a red square in 0.346 seconds and red, blue, green in order in a short clip in 1.007 seconds. A separate comparison records an error on a rotated serial number and successful reading of the upright version. [API examples](reproduce.md#connect-an-api-client) · [Media receipts](../results/native-media-smoke.json) · [Vision comparison](../results/vision-comparison-2026-11-20.json)

**Prefill** processes the supplied tokens and builds the GDN recurrent state, convolution history, and QSA key/value (KV) records before normal generation. A matching cached prefix can resume from saved state. In a four-turn follow-up test, at least 99.3% of each follow-up prompt was reused. **Decode** appends generated tokens, repeatedly updating the state. The engine can batch work from up to five slots, sharing GPU operations while retaining each stream’s own history and output. A CUDA graph records a repeatable sequence of GPU operations so a matching decode shape can be launched with less CPU overhead. TensorFold’s patched decode code includes graph paths. The throughput receipts time the whole request path without counting graph replays. [Reuse and concurrency checks](../results/validation-2026-11-20.json) · [Engine cache and decode implementation](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark-TensorFold/blob/b956dba8a468f1cf376d60bbbd9b9ed51ff2f0a9/patches/0003-kv-cache-fp8.patch)

During decode the MTP module can chain up to six proposals for target verification. The `-0.4` configuration uses a running product of proposal probabilities to end the chain as confidence falls. `shared_drafts=0` keeps the confidence rule active beside other streams. Imagine a greedy draft proposes “counter next door” and the target agrees on “counter next” but selects “to” at the next position. Only the agreed prefix survives, followed by the target’s correction. The next round starts from the committed prefix. Verification can thus amortize a large model pass over several new positions. The local parity test compared five greedy replies with drafting enabled and disabled, counted 291 accepted drafts, and also matched five concurrent replies against serial execution. That checks these prompts and this quantized target. The sampling throughput run measures a different property. [Observed draft settings](../results/running-profile.json) · [Draft rule](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark-TensorFold/blob/b956dba8a468f1cf376d60bbbd9b9ed51ff2f0a9/README.md) · [Parity checks](../results/validation-2026-11-20.json)

### What the capacity and timing figures tell you

Each slot has a configured 262,144-token window shared by its prompt and requested reply. The engine uses FP8 for its main attention KV. Its startup accounting reported 4.83 GiB per full slot with MTP enabled, about 24.2 GiB for five. That budget covers full windows even if current prompts are short. The 9 GiB reserve protects headroom in the memory calculation. The 32.50 GiB Linux reported as available at idle is a separate observation after startup. A context boundary test checked admission at different requested budgets with a short prompt. Actual reading of a long input was tested separately. [Memory accounting](benchmarking.md#ram-under-decode-load) · [Capacity checks](../results/validation-2026-11-20.json)

For one through five simultaneous 400-token prose replies, the best aggregate decode rates across three waves were **56.0, 82.6, 102.3, 119.9 and 125.6 tokens/s**. The single-stream time to first token (TTFT) was 63 ms. At five streams the median reader saw 25.8 tokens/s and waited 181 ms for the first streamed reasoning or answer token. The benchmark uses thinking on, temperature 0.7, top-p 1 and top-k 20. Temperature scales the scores before sampling, top-k keeps at most 20 candidates and top-p 1 permits their full probability mass. The aggregate clock spans the earliest first token to the latest last token and excludes each stream’s first token from the numerator. [Decode data](../results/decode-prose-thinking-on-2026-11-20.json) · [Timing method](benchmarking.md#thinking-on-prose)

Seven independent fresh retrieval prompts ranged from 4,084 to 200,007 input tokens and reused two template tokens each. At 200,007 input tokens the engine processed uncached input at **2,099 tokens/s** and the client waited **95.34 seconds** for the first token. All seven returned the expected marker. This test divides uncached input by *engine prefill time*. The five-stream decode measurement uses short prompts. Combining those two numbers would describe a workload the benchmark never ran.
